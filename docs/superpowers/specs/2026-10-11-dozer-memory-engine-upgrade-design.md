# Dozer Memory 轻量记忆引擎升级

> 日期：2026-10-11。状态：草案，待审阅；尚未实施。
> 目标：将项目面板的共享记忆升级为支持来源追踪、任务召回和经验演进的项目级记忆引擎。
> 前置设计：[Agent 记忆共享模块](2026-09-23-agent-memory-sharing-design.md)、[Project 服务边界](2026-10-10-project-services-design.md)。

## 1. 设计结论

沿用 `dozerd + Rust + SQLite + dozer-mcp + MemoryService`。SQLite 继续作为权威数据源，项目面板作为浏览和治理入口，各 Agent 共用相同的存储与检索接口。

借鉴 Hindsight 的 Retain / Recall / Reflect 分工：形成可追溯记忆、按任务召回、基于证据归纳。本文定义的是 Dozer 自有的轻量实现，不承诺 Hindsight API 兼容或同等检索效果，不引入其服务作为运行依赖。

- **P1：可用的记忆引擎。** 来源追踪、结构化类型、全文召回、替代关系、生命周期、MCP 和面板闭环。
- **P2：语义与归纳。** 可选向量检索、由当前 Agent 执行的有依据归纳、“整理记忆”交互。
- **后续候选：** 自动会话提炼、更多实体关系、多跳召回；不属于本次交付承诺。

核心原则：存储、校验和检索由 dozerd 承担；语义提炼和推理由 Agent 承担。P1 不要求模型服务、API Key 或常驻推理进程。

## 2. 当前实现与差距

以本次读到的代码为准：

| 层 | 当前实现 | 升级职责 |
|---|---|---|
| 存储 | `crates/dozerd/src/memory.rs`：`memories`、`memory_history`，按项目和标题 upsert | 迁移、事务、来源、版本、关系、全文索引 |
| 共享类型 | `crates/dozer-model/src/project.rs` | 新增请求数据、召回结果、来源和生命周期类型 |
| 协议与客户端 | `crates/dozer-core/src/protocol.rs`、`crates/dozer-client/src/lib.rs` | 新请求与回复、兼容已有 CRUD |
| 服务边界 | `crates/dozer-services/src/lib.rs` 中的 `MemoryService` | 扩展召回和结构化写入，不让面板直接依赖 Client |
| MCP | `crates/dozer-mcp/src/server.rs` | 继续支持 `write_memory/list_memories/get_memory`，增加新工具 |
| 面板 | `crates/dozer-app/src/extensions/project.rs` 及 `project/` | 搜索、筛选、来源、替代关系和状态治理 |

已有数据包含标题、自由分类、摘要、正文、创建/修改时间和操作人；历史保留完整文本快照。现有写入按标题覆盖，尚无语义召回、来源证据或过时状态。当前主记录和历史写入分开执行，升级时必须改成同一事务。

此前 spec 的“搜索、乐观锁不做”在本次 P1 范围内被替代；项目隔离、SQLite 权威、人类管理删除以及历史保留的原则继续有效。

## 3. 用户场景与边界

### 3.1 典型闭环

1. Agent 修复“热重载导致重复初始化”，写入经验，关联来源会话及涉及文件。
2. 下次处理类似故障，Agent 用任务描述调用 `recall_memories`，得到经验摘要、命中原因和来源，再按需读取全文。
3. 初始化机制改变后，Agent 创建新结论并显式替代旧结论。旧记忆退出默认召回，用户仍能查阅沿革。
4. P2 中，Agent 从多次修复归纳出“初始化约束”，引用具体记忆版本，作为独立归纳条目保存。

### 3.2 保证与非目标

- 所有查询、来源引用和关系操作限定在当前项目；MCP 的项目归属由会话解析，不接受任意项目覆盖。
- 成功写入后，其他连接同一 daemon 的 Agent 可立即读到；提交事务失败则整体不生效。
- MCP 工具描述引导 Agent 在任务开始召回、任务完成后保留长期结论，但不能保证宿主 Agent 一定调用工具。
- P1 不自动摄取全部聊天、终端输出、Agent 私有记忆目录，也不把项目指令文件批量导入记忆。
- 本次不做跨项目全局记忆、独立图数据库、常驻后台模型、无人工触发的全库整理。
- 记忆是带来源的上下文，不自动提升为系统指令；模型生成内容不因存入数据库而成为已验证事实。

## 4. P1 数据模型

以下为逻辑模型；具体 DDL 在实施时按现有数据库迁移设施落地。新增结构使用 `memory_` 前缀，避免影响同库其他模块。

### 4.1 记忆主记录

保留现有字段和 `(project_id, title)` 唯一约束，新增：

| 字段 | 语义 / 默认值 |
|---|---|
| `memory_type` | `note / fact / decision / experience / preference / synthesis`；旧数据为 `note` |
| `status` | `active / deprecated / superseded`；默认 `active` |
| `pinned` | 默认 false；仅作为有效记忆的排序信号，不覆盖状态过滤 |
| `revision` | 从 1 开始，任何有效变更递增 |
| `event_ms` | 可空，事实或事件实际发生时间；不以修改时间伪装事件时间 |

`kind` 继续接受旧的自由文本值，不强制映射 `user/feedback/project/reference`。`memory_type` 表示知识性质，`kind` 保留原有分类，标签表达模块或主题，三者互不覆盖。

旧数据不猜测来源、事件时间或知识类型。P1 允许 `synthesis` 类型以便兼容后续，但不提供自动归纳流程。

### 4.2 来源与标签

新增 `memory_sources`：`id, project_id, memory_id, source_type, locator_json, excerpt, recorded_ms, recorded_by`。

- `source_type`：`session / file / url / manual / legacy`。
- 会话定位包含 session ID，可选消息/事件定位符；文件定位包含项目相对路径，可选行号和 commit；URL 保存原地址。
- MCP 写入自动附上当前会话来源，调用方附加的来源另行保存。系统来源不能通过普通内容更新移除。
- 人工创建自动附上 `manual`；迁移记录使用 `legacy`，UI 明示“历史数据，来源未记录”。
- `excerpt` 是可选的短证据摘录，不复制完整会话或文件；最多 2,000 个 Unicode 字符。
- 会话必须属于当前项目；文件路径规范化并限制在项目内。URL 只保存和展示，不在写入时抓取。
- 来源目标消失后保留定位信息并显示“来源不可用”，不让详情页整体失败。

新增 `memory_tags(project_id, memory_id, tag)`，联合唯一。标签去首尾空白、去重，单条最多 32 个；不通过模糊相似度自动改名或合并。

### 4.3 替代关系

新增 `memory_relations(project_id, from_id, to_id, relation_type, created_ms, created_by)`；P1 仅开放 `supersedes`：`新记忆 → 被替代的旧记忆`。

- 两端必须存在且属于同一项目；禁止自指和环。
- 替代是显式操作，不由文本相似度自动推断。一次可替代多条旧记忆。
- 创建关系和把旧记忆改为 `superseded` 必须在同一事务内完成，涉及的旧记录均递增版本并留历史。
- 被替代的记录默认不可再次替代；并发替代返回冲突，调用方重新读取后决定是否替代当前后继。
- 要恢复旧记忆，必须显式撤销其入向替代关系并留审计记录，不能只把状态改成 active。
- 删除当前后继不会自动复活旧记忆。删除前 UI 展示受影响关系；事务内移除活动关系，历史保留关系快照。

### 4.4 历史、事务与删除

扩展历史记录以保存 `revision` 和新增元数据快照，覆盖类型、状态、固定标记、标签、来源、关系。旧历史缺失的字段展示为“未记录”，不回填成当时已存在的证据。

创建、编辑、旧工具 upsert、状态变更、替代和删除，均将主记录、附属表、索引、相关历史写入放在同一事务内。历史按 `(changed_ms DESC, id DESC)` 稳定排序，避免同毫秒顺序不确定。

继续保留人工删除、历史可查的语义；MCP 不新增删除工具。删除同时清理当前来源、标签、全文索引和活动关系，历史不级联删除。UI 明示删除不会擦除历史证据。

## 5. P1 写入与兼容语义

### 5.1 新入口

新增 `retain_memory`，按以下形状接收结构化数据：

```text
retain_memory(
  title, body, description?, memory_type?, kind?, tags?, sources?, event_ms?,
  id?, expected_revision?,
  supersedes?: [{ id, expected_revision }],
  request_id
)
```

- 不带 `id` 为创建；标题重复返回 `conflict` 和现有 ID，不能静默覆盖。完全相同内容但不同标题允许保存，P1 不宣称语义去重。
- 带 `id` 为修改，必须传 `expected_revision`；版本不同返回 `conflict`，不会覆盖他人修改。
- 创建和修改均校验标题、正文非空；标题最多 256 字符，正文最多 64 KiB UTF-8，来源最多 32 条。旧记录仍可读取；旧写入保留原来的空文本兼容行为。
- 更新时未提供的可选字段保持原值；标签/用户来源传空数组表示清空可编辑部分，系统会话来源追加保留。清除事件时间使用显式 null，与缺省区分。
- `request_id` 在项目及调用者会话作用域内唯一：相同请求重试返回原结果；同键不同载荷返回冲突。去重记录与写事务一起提交，保存载荷哈希和原结果，P1 不自动清理。
- `supersedes` 中的每条记录都必须通过版本校验；任意一条失败则整体回滚。
- 返回 `id, revision, outcome(created/updated/replayed), status` 和必要的详情。

另增 `update_memory_state(id, expected_revision, status?, pinned?, reason?)`，允许 active 与 deprecated 之间变更及固定/取消固定。superseded 只能由关系操作产生或通过显式撤销替代恢复，不能直接赋值。状态变化需提供 reason。

撤销替代由 UI 使用专用服务操作完成，校验新旧两端版本，删除指定关系；仅在旧记录不存在其他入向替代关系时恢复 active，并记录原因。P1 MCP 不开放撤销工具。

### 5.2 旧接口

- 保留 `write_memory/list_memories/get_memory` 名称及既有必需字段。旧调用方无需先迁移。
- `write_memory` 继续按标题 upsert、后写覆盖正文；明确这是旧入口的兼容例外，不具备乐观锁保证。任何写入仍递增 revision，使新入口能检测冲突。
- 旧工具不得清空新增来源、类型、标签和状态，也不得让过时记忆复活；更新非 active 条目时在结果中附加状态提示。
- `list_memories` 保留列出全部当前记录的语义；默认仅 active 的规则属于新召回接口，不悄悄改变旧列表。
- `get_memory` 继续支持标题或数字 ID。新接口统一用明确 ID，避开纯数字标题歧义。
- 面板升级后编辑按 ID 和版本提交；重命名更新原条目，不因标题变化意外新建。

新增协议能力需显式协商或探测：新客户端连接旧 daemon 时禁用新功能并显示需升级，不把“不支持请求”呈现为空结果。新 daemon 继续接受旧请求；新增回复字段需验证旧客户端反序列化兼容性。

## 6. P1 召回契约

```text
recall_memories(
  query,
  memory_types?, kinds?, tags?, statuses?,
  time_field?: event_ms | updated_ms,
  from_ms?, to_ms?, limit? = 10, max_chars? = 8000
)
```

- 项目由会话解析；默认 `statuses=[active]`，可显式查询过时/被替代记录。
- `limit` 范围 1–50，`max_chars` 范围 500–20000；超出范围返回参数错误。
- 各过滤维度之间为 AND，同一类型/状态数组内为 OR；tags 表示全部指定标签都需满足。空数组视为未过滤。
- 时间范围为闭区间，默认过滤 updated_ms；选 event_ms 时不返回事件时间未知的记录。
- 空白 query 返回参数错误；浏览全量记录仍使用列表接口。
- 返回项包括 `id, revision, title, description, snippet, memory_type, status, tags, sources` 摘要、`match_reasons`、可解释的相关性分值及替代提示。
- 分值仅用于同一查询排序，不是事实置信度，不承诺跨查询可比较。
- 返回 `truncated` 和实际返回数量。字符预算作用于条目文本负载（标题、摘要、片段、来源摘录），协议键和 ID 不计；逐项裁剪片段，完整条目装不下时停止，不截断 JSON。全文由 get 获取。

### 6.1 全文搜索与中文

使用 SQLite FTS5 派生索引，索引标题、摘要、正文、标签，主记录仍是权威。实现前验证 bundled SQLite 的 FTS5 能力，缺失时给明确错误，不静默退化成全表 LIKE。

P1 采用应用层统一分词：英文及标识符拆词，同时保留完整标识符；连续汉字生成单字和相邻双字 token。索引和查询共用同一算法并保存 tokenizer 版本。这样覆盖中文子串与中英文混合查询，但不声称支持同义词理解。

查询文本作为普通文本解析，转义后构造受控 MATCH 表达式，不直接执行用户输入的 FTS 语法。关键词生成有数量上限（64 个），超过上限返回可理解的参数错误。

候选在项目、状态和其他过滤条件下产生，不能先取全局 top-k 再过滤项目。按覆盖词数、字段加权 BM25（标题 > 摘要/标签 > 正文）排序；同等相关性下考虑 pinned、更新时间，最后以 ID 稳定排序。固定标记不能使无关记录挤入候选。

P1 仅返回直接匹配及其替代提示，不自动做多跳图扩展。默认查询命中被替代的旧词但未命中新记录时可以无结果，不偷偷把旧结论当有效事实返回；用户可打开“包含历史”查看。

### 6.2 效果与延迟验收

建立至少 30 条人工标注查询，覆盖中文、中英文混合、文件名/符号、决策沿革、无结果和项目隔离；每条声明期望 ID 或允许无结果。关键词可解查询的 Hit@5 目标 ≥ 90%，同义改写单列为 P2 基线，不混入 P1 承诺。

在记录硬件、构建模式和数据规模的本地基准中，以单项目 10,000 条、平均正文约 2 KiB 为测试集，热索引 Recall 存储层 P95 目标 ≤ 100 ms，冷启动和 IPC 延迟分别报告。该值是待验证的验收目标，不是已测结果；未达标需记录原因和调整方案。

## 7. 项目面板与 Agent 工作流

### 7.1 P1 面板

- 保留“共享记忆”入口，增加搜索、知识类型、标签和状态筛选；普通浏览默认展示 active，可选择全部状态。
- 搜索输入 debounce 250 ms。请求携带 project ID 和递增查询代数；切项目或变更查询后丢弃过期回复。
- 列表展示类型、摘要、状态、最近修改者；搜索态补充命中片段。空列表、无匹配、正在加载和读取失败是不同状态。
- 详情展示正文、来源链接、标签、事件时间、被什么替代/替代了什么、版本历史。
- 支持创建、按版本编辑、固定、标为过时、显式替代、撤销替代和删除。替代操作选新旧条目并展示方向，避免语义反转。
- 编辑冲突保留草稿，提供重新读取和比较当前版本的入口，不自动重试覆盖。
- 来源会话或文件通过已有打开路径接入；来源消失保留定位文本和摘录。搜索片段按普通文本渲染。
- 延续服务层读失败约定：保留旧数据并标识未刷新；Unavailable 不重复弹窗，其他错误沿用去重提示。写失败保留输入。
- P1 不展示尚不可用的“整理记忆”按钮。

### 7.2 MCP 使用引导

工具描述推荐：任务开始先用任务内容召回，按需 get 全文；出现长期有效的新事实/决策/经验后 retain；发现旧结论失效时显式替代。临时进度、未验证猜测不默认记作事实。

保持各 Agent 共用同一接口，不为不同 CLI 维护多套记忆副本。没有 MCP 通道的 Agent 仍是覆盖缺口；自动注入上下文不是 P1 保证。

## 8. P2：语义召回与归纳

### 8.1 可选语义检索

增加可配置 embedding provider，用户启用后才建立向量。记录模型、维度、内容哈希及索引版本；模型切换需重建对应索引。SQLite 保存权威正文，向量为可丢弃重建的派生数据。

全文与向量候选融合后仍遵守项目、状态、时间过滤及输出预算；模型不可用时退回 P1 检索并返回降级说明。不得在持有 SQLite 连接锁时调用远程服务。具体 provider、向量扩展和融合参数由独立 P2 实施设计及中英文评测决定。

### 8.2 Agent 执行 Reflect

“整理记忆”让用户选择范围并使用当前可执行 Agent：召回证据 → 读取全文 → 生成归纳草稿 → 展示引用 → 用户保存。没有可用 Agent 时说明原因，不启动隐式后台模型。

Reflect 是工作流，不在 P1 增加一个只能检索却命名为 `reflect_memory` 的工具。P2 是否封装专门任务接口，在 Agent 调度接入设计中确定。

- 归纳以独立 `synthesis` 条目保存，并增加 `derived_from` 关系，引用原记忆 ID 和具体 revision。
- 区分原始事实与推断，保留证据，不默认替代原记录。
- 引用记忆修订、失效或删除后，归纳标记“依据已变化”，默认召回排除待复核归纳；复核后才能恢复。
- P2 需扩展关系快照以保留被引用的历史版本；不能只引用随时变化的当前正文。
- 不让归纳无限递归引用归纳：首版整理直接读取原始证据，限制单次条目数和文本预算。

## 9. 迁移与发布

1. 使用 memory 模块自己的 schema 版本，不能直接占用共享 dozer.db 的全局版本号而影响其他模块。
2. 迁移前创建一致性数据库备份（SQLite backup 或等价方案，包含 WAL 中已提交数据），记录路径及旧版本。备份失败则不继续迁移。
3. 在事务中新增字段和表、迁移旧记忆；ID、标题、正文、原分类、时间、操作人及旧历史全部保留。旧条目设为 note/active/revision=1，补 legacy 来源。
4. 构建全文索引并校验条目计数；失败回滚，不留下半迁移状态。迁移期间不接收记忆写入，完成后开放服务。
5. 重启重复执行无重复来源、历史或关系。索引损坏可从权威记录重建；重建期间显示明确不可用状态，不返回伪空结果。
6. schema 升级后不支持旧 daemon 直接写入该库。回退通过停服及恢复备份完成；恢复前备份升级后的数据库，明确迁移后写入不会自动合入旧版本。

旧 MCP 客户端兼容与旧 daemon 数据库回退是两件事。发布说明分别描述，不把保留旧工具等同于支持旧二进制安全写新库。

## 10. 实施边界与错误处理

- `dozer-model` 放纯数据类型；`dozer-services` 扩展小 trait，继续只依赖模型层；`Client` 承担协议适配；SQL 和 tokenizer 放 daemon 内部。
- 新功能经过 `MemoryService` 进入面板，不恢复面板直接调用 Client 的路径。入参采用结构体，避免继续增加位置参数。
- 复用现有 ServiceError 分类，同时在新回复中提供可判定的业务错误码：`invalid_argument / not_found / conflict / unsupported / index_unavailable`。不要靠解析中文错误文本分支。
- 跨项目 ID 与不存在 ID 对外一致按 not_found 处理。来源、关系、历史、索引查询全部带项目约束。
- MCP 操作人由现有会话解析取得，UI 操作人延续 user；旧 actor 显示值保持原样，不在迁移时伪造规范化身份。
- 记录操作耗时、结果数、冲突数和索引版本；默认日志不输出正文、来源摘录或完整搜索文本。
- P1 不引入长期持锁网络操作，不执行记忆正文中的指令，不在来源字段驱动任意本地文件读取。

## 11. 验收与测试

### P1 必须通过

1. **迁移：** 旧库 fixture 升级后原数据和历史保持；重复迁移幂等；故障注入不会留下半迁移或损失原库。
2. **事务：** 主记录/历史/来源/关系/索引任一步失败全部回滚；写入成功后立即可召回；删除后默认和历史状态搜索均不返回已删除正文。
3. **版本与重试：** 并发编辑只允许匹配版本者成功；同 request_id 重试无重复历史；不同载荷复用键冲突；旧工具写入也使 revision 递增。
4. **关系：** 自指、环、跨项目和过期版本被拒绝；替代原子完成；撤销有历史；删除后继不自动复活旧记录。
5. **召回：** 中文、混合标识符、特殊符号不会造成 MATCH 错误；项目和状态隔离正确；排序稳定；字符预算、limit 和时间边界有测试；效果和性能基准达到第 6 节目标或明确阻断发布。
6. **兼容：** 原有 MCP memory 集成测试继续通过；新工具覆盖 retain → recall → get → supersede；旧写入保留新增元数据；新旧协议能力不匹配给出明确提示。
7. **面板：** 用 Fake MemoryService 覆盖过期查询、切项目、读失败保留数据、编辑冲突保留草稿；真实 GUI 验收来源跳转、中文搜索、替代沿革、删除提示。
8. **工程检查：** 受影响 crate 测试、格式检查及现有架构边界检查通过；不引入新的面板 Client 依赖。实现时记录现有基线失败，不能把未运行或原有失败报告为通过。

### P2 追加门槛

- 中英文语义查询单独评测，对比 P1 的召回收益、延迟和模型成本。
- provider 不可用时 P1 可用；内容或模型变化后旧向量不被误用。
- 归纳必须可定位到原始版本；依据变化会进入复核状态；Agent 中断不产生半成品正式记忆。

## 12. 实施顺序

1. 迁移与事务基础、来源/版本/关系模型，连同故障和兼容测试。
2. 全文索引、中文 tokenizer、召回契约和评测数据集。
3. 协议、Client、MemoryService 与 MCP 新旧入口闭环。
4. 面板搜索、详情和治理操作，完成 P1 验收后发布。
5. 另立 P2 实施设计，确定 embedding 接入及 Agent 整理任务协议后开发。

P1 的发布标准是：Agent 能按任务找到有效且可追溯的记忆，用户能管理结论的演进，旧数据和调用方式有清晰兼容路径。语义检索和归纳未完成不影响 P1 独立交付。
