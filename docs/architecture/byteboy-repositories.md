# ByteBoy 多仓治理

> 状态：生效。最后更新：2026-10-08。

## 仓库边界

ByteBoy 采用“平台能力独立仓库、产品独立仓库、组合版本单独记录”的
polyrepo 结构：

| 仓库 | 类型 | 职责 |
|---|---|---|
| `byteui` | 平台库 | 原生 UI 组件、主题与交互原语 |
| `bytegit` | 平台库 | 本地 Git 数据与操作能力 |
| `bytehost` | 平台库 | 应用宿主平台库：应用模型/安装计划/生命周期/来源、进程型应用监管、受管运行时、origin gateway,以及界面框架无关的应用面板与 webview 安全策略。dozer 已接入 `v0.1.0` |
| `dozer` | 产品 | AI 工作治理与验收 |
| `digger` | 产品 | 内容生产产品；只复用平台能力，不依赖 dozer 内部实现 |
| `byteboy-workspace` | 集成（待建立） | 固定一组已验证的仓库提交并运行跨仓测试，不承载产品代码 |

依赖只能从产品指向平台库。平台库不得依赖 `dozer` 或 `digger`，两个产品
也不得相互依赖。尚未稳定、只有一个消费者的代码留在产品仓；至少有两个
真实消费者且语义稳定后再提取到平台仓。

## 依赖与版本

- 正式依赖一律固定 Git tag；禁止依赖 `main`、分支或浮动 revision。
- 每个仓库独立使用 SemVer、独立发布、独立维护 changelog。
- 产品仓提交 lockfile，保证发布构建可复现。
- 本地跨仓联调使用不提交的 `.cargo/config.toml` `[patch]`，不得把相对路径
  依赖写进正式 `Cargo.toml`。
- 公共协议和公开类型遵守向后兼容；平台库不得向调用方泄漏可替换后端的
  类型，例如 `bytegit` 不公开 `git2` 类型。

## 跨仓改动

一次跨仓功能按以下顺序交付：

1. 平台仓增加兼容能力和测试，发布新 tag。
2. 产品仓升级 tag 并完成产品侧迁移。
3. 删除产品仓里的重复实现。
4. 集成仓更新组件提交，运行组合构建与 smoke test。

联调期间可以临时 patch 到平台仓工作区，但产品提交必须回到正式 tag。不同
仓库的 PR 相互链接，不能靠合并顺序之外的隐含状态才能构建。

## Git submodule 的使用范围

只有 `byteboy-workspace` 可以把各仓库登记为 submodule，用来记录经过验证的
提交组合。`dozer`、`digger` 和平台仓均不得嵌套其他项目的 submodule；代码
依赖由 Cargo、npm 等包管理器解析。

## 当前迁移顺序

1. `byteui`：已独立，dozer 当前固定 `v0.4.1`。
2. `bytegit`：已完成 `v0.1.0` 骨架；从 `repo_root` 开始按纵向切片迁移。
3. `bytehost`：已建仓并发布 `v0.1.0`（应用宿主平台库），dozer 已改为按 tag 消费。
   注意：`bytehost` 目前的职责是**应用宿主平台库**（见上表）；早期设想的
   “agent、进程、PTY、session 与 Host 契约”那条职责尚未落位，单独标为待定，
   不要再用 `bytehost` 这个名字指代那部分。
4. `digger`：在 Host 契约稳定前保持产品设计仓，不复制 dozer 面板实现。
5. `byteboy-workspace`：至少三个可构建仓库接入后建立，负责组合版本和跨仓 CI。

每次新增独立仓库前必须回答：公开 API 是什么、谁是第二个消费者、兼容性由
谁维护、如何独立测试和发布。回答不完整时，不拆仓。
