# bytehost H8 评估:状态与消息信封动态化,现在值不值得做?

> 日期:2026-10-04。依据:设计文档 P4("H7 完成后用 H0 的度量重新评估")。`main` = `c23b33a4`(H7a 之后),对照 H0 基线 `4845fb85`。
> 本文只给数据和建议,**不替用户裁决**。不含任何代码改动。

## 1. 数据:H1–H7a 之后,host 对面板的"点名面积"几乎没变

同口径对照(`git grep`,`crates/dozer-app/src`):

| `PanelKind::<变体>` 点名行 | 763 | **893**(+130) | 生产 464、测试 429 |

**生产代码里 `PanelKind::<变体>` 点名最多的地方**(估计,未逐行分类):`workspace/view.rs` 70、`app/view.rs` 61、`app/layout.rs` 50、`app/update.rs` 49、`app/app.rs` 48、`platform/window_events.rs` 43、`webview_geometry.rs` 37——前两个是"给每个面板渲染一份壳",后几个是按面板各写一段的布局/几何/事件代码。

**结论 1:H1–H7a 达成的是"契约和可测性",不是"host 变小"。** 面板不再引用 `App`/`Workspace`(门禁已清零)、`HoverId` 不再点名面板按钮、`PanelDims` 有统一访问器、面板有了 `PanelIo`/`HostOutbox`/`ActivationCtx`、默认布局与元数据由清单驱动,并且新增了约 70 个原先不存在的测试。但 host 里"替面板编排"的主体(6.4k 行的 `update.rs`、4.5k 行的 `window_events.rs`、6.2k 行的 `app.rs`)几乎原样在那里。这不是迁移失败,而是前面的切片刻意只动**边界**,没动**主体**。

## 2. H8 要动的是什么

H8 = 把下面三样从"点名 12 个面板的具体字段/变体"变成"按面板 id 取的动态容器":

1. `Workspace` 的约 12 组面板状态字段(`todo`、`usage`、`codehealth`、`conversations`、`group_chat`、`database`、`ssh`、`files`、`project_panel`、`browser`、`agent_context`、`review*`……共 44 个字段里的大部分);
2. `Message` 的 19 个面板包装变体与对应的 `App::update` 分派(153 条面板专属臂);
3. `PanelDims` 的 23 个按面板展开的字段,以及 `webview_geometry`/`app/layout.rs`/`workspace/view.rs` 里对 12 个面板各写一段的代码。

这是一次**横跨 `update.rs`、`window_events.rs`、`app.rs`、`view.rs`、`layout.rs`、`webview_geometry.rs` 的重写**(合计约 2.7 万行文件),不是机械替换:动态容器要决定面板状态的类型擦除方式(`Box<dyn Any>`?面板 trait?)、消息怎么路由(`Box<dyn Any>` 信封还是每面板一个 `enum PanelMsg`)、`view` 怎么按 id 分发——这些都会改变编译期穷举检查的现状(现在新增面板漏改会编译失败,动态化之后变成运行时问题)。

## 3. 收益在哪里,什么时候兑现

H8 的收益只有在**存在第二个消费者**时才兑现:

- Digger 只需要部分面板时,不动态化也能"不实例化某些面板"(清单已经支持更小的集合),但**编译期仍要带着全部 12 个面板的状态与消息类型**——也就是 host 仍不是一个能独立编译的东西。
- 要真正把 host 拆成独立 crate,H8 **不是唯一的前置**。H0 汇总里还有至少三个同量级的阻塞:`dozer-core::protocol`(3085 行,含全部 Dozer 领域类型)的归属(O7)、Preview 业务有两个实例且 webview id 编码里藏着面板名(S4/S5)、终端区与 Agent/Ssh 面板不可分(O1/O6)。只做 H8、不解这些,仍拆不出 crate。
- 目前没有任何落地中的消费者在等这件事:没有一条已排期的功能因为 host 没动态化而做不了。

**结论 2:H8 是一个"为尚未出现的需求预付"的重写,风险(编译期保证退化、2.7 万行文件同时改)与收益(目前为零)不对称。**

## 4. 选项

| 选项 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **A. 在 H7a 停下(推荐)** | 结构迁移到此为止;门禁继续当棘轮;H7b/H8 记为"有第二个消费者的具体需求出现时再做" | 0 | 无;唯一的代价是如果 Digger 很快需要复用面板,届时要从零排期 |
| **B. 先做 O12 可行性探针(推荐作为 A 的补充)** | 选一个纯展示、依赖少的面板(Usage 或 Todo),写**规格不写迁移**:"一个面板 + 最小 host + fake 服务就能跑"的形式定义,并列出它实际还缺哪些 host 能力 | 一份 spec(约 1–2 天量级) | 低;产出会直接告诉我们"第二个消费者"到底需要 host 提供什么,从而判断 H8 的真实范围 |
| C. 直接做 H8(全量) | 如 §2 | 很大,单独立项 | 高:编译期穷举保证退化;且不解 O7/S4/S5/O1 仍拆不出 crate |
| D. H8-lite:只把**一个**面板(如 GroupChat)的状态与消息动态化当试点 | 验证"类型擦除+路由"的写法与成本 | 中 | 中:试点面板的写法未必能推广;但能把 H8 的最大未知数(§2 的三个设计问题)变成数据 |

## 5. 建议

1. **默认走 A+B:** 把 H7a 当作这一系列的自然停顿点。下一步不再做结构迁移,而是做 B(O12 探针规格),用它回答"第二个消费者到底要什么";H7b/H8 在探针有结论、且确有消费者时再排。
2. **门禁保持棘轮:** `check_panel_boundary.py` 的基线(`R-HOST-PANEL-ARMS 95` 等)继续只降不升,防止已经收口的边界回退。
3. **如果用户判断 Digger 复用面板是近期要事:** 优先选 D(单面板试点)而不是 C,因为它能在不改全局的前提下暴露 §2 的设计问题;同时要并行回答 O7(protocol 归属),否则 host 仍拆不出去。
4. **同时承认一个事实:** 如果这一系列的目标是"让 `app/update.rs`/`window_events.rs` 变小、更好维护",那么 H1–H7a 的直接效果很有限(−1.5%/−1.1%)。要降低这两个文件的体积,更直接的路径是**按面板把消息臂搬进各面板的 `update`/钩子**(H5/H6 的做法),但那条路上剩下的臂大多依赖窗口层上下文(焦点意图、剪贴板、webview 池,即 H5b),需要先让窗口层上下文可注入——它与 H8 是两件独立的事。
