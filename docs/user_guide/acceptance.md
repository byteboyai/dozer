# 验收闭环

这是 Dozer 的核心——"目标/验收标准 → agent 交付 → 验收(通过/打回) → 演进史"。它把资深创作者验收产出物的判断结构外化成了产品功能,而不是把这件事继续留在你脑子里凭感觉判断。

## 第一步:写 `.dozer/goal.md`

Dozer **没有图形化的目标/验收标准创建入口**——你(或者你让 agent 帮你)得手写这个文件,放在项目根目录的 `.dozer/goal.md`。格式很简单,是普通 Markdown:

```markdown
把登录页迁移到新的表单组件

- [ ] 邮箱/密码校验保留原有规则
- [ ] 提交成功后跳转到 /dashboard
- [ ] 现有的单元测试全部通过
```

- **第一个非空行**是目标标题。
- 之后每一行 `- [ ]` / `- [x]` 是一条验收标准。

如果项目里还没有这个文件,验收面板会提示"未定标",告诉你该怎么写这一句——Dozer 只负责读和解析这个文件,不负责生成它。

## 第二步:让 agent 干活

正常在终端里跟 agent 交互(见 [Agent 会话](agents.md))。Dozer 在后台会一直用 git 状态判断"这一轮有没有产出待审的东西"——工作区是脏的,或者 HEAD 相对上一次验收通过的位置(或本轮开始时)已经前移。

一轮 agent 报告结束(hook 上报 `TurnEnded`)且检测到有改动时,右侧图标栏的**验收**图标上会出现一个金色小红点提醒你。

## 第三步:进入验收视图

点验收图标(不管有没有红点,随时都能进)。视图分三块:

- **左**——改动文件列表,每个文件显示 `+新增 −删除` 行数,点一个文件会懒加载并展开一份内联的彩色统一 diff(基于 `libgit2` 计算,单文件超过约 2 万字符会截断)。
- **中/标准区**——目标标题 + 从 `goal.md` 解析出的验收标准清单,逐条点击勾选(纯 UI checklist,勾选本身不会自动拦截你点"通过")。
- **意见框**——自由文本,写下你对这一轮交付的评价;如果你选择"打回",这段文字会被原样发回 agent。

## 第四步:两个动作

- **"通过·沉淀"**(金色主按钮)——要求当前工作区是干净的(没有未提交改动,否则会报错拒绝);执行后会在当前 HEAD 打一个 `refs/dozer/accepted/N` 的 git ref(N 按仓库自增),并把这次验收(目标标题、勾选了哪些标准、通过与否、意见、ref 名、时间戳)记进 `dozerd` 的 SQLite 库。这个 ref 就是"演进史"的字面实现——`git log --oneline --decorate` 能直接看到这条历史。
- **"打回并注回"**(红色描边按钮)——把 `[Dozer 验收打回] {你写的意见}` 这段文本,当作**你亲手在那个 agent 的终端里打的字**直接发回去(不是另开一个新会话),然后关掉当前的验收视图。如果来源会话已经结束了,会给你一个内联错误提示,不会悄悄把你的意见丢掉。

两个动作都是**按钮点击,没有键盘快捷键**,也没有二次确认弹窗——点"通过"就是立即生效(前提是工作区干净这一条硬性检查)。

## 数据存在哪

- 验收记录(谁通过了什么、打回了什么、意见是什么)存在 `dozerd` 的本地 SQLite 里。
- "到底改了什么"这件事的真相来源是 **git 本身**——`refs/dozer/accepted/N` 这条 ref 链,不是 Dozer 自己维护的一份私有 diff 存档。这意味着就算完全脱离 Dozer,你也能用普通 git 工具追溯每一次验收通过对应的具体提交。

## 关口松紧完全由你自己把握

Dozer 不强制"标准全勾选才能通过"、不强制"必须先定标才能开始干活"——这些关口的位置和松紧,是留给你按实际项目节奏调整的,不是硬编码在产品里的姿态。
